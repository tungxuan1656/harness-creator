# harness-slim

Compact skill for building and auditing harnesses around AI coding agents.

Provides five things agents need: instructions, state, verification, scope boundaries, and lifecycle handoff.

## Install

```bash
npx skills add tungxuan1656/harness-slim --skill harness-slim
```

Or copy `skills/harness-slim/` into your skill path.

## Use

```bash
# Create harness
node skills/harness-slim/scripts/create-harness.mjs --target /path/to/project

# Check harness state from the generated project root
./scripts/check-state.sh feature_index.json

# Validate structure
node skills/harness-slim/scripts/validate-harness.mjs --target /path/to/project

# HTML report
node skills/harness-slim/scripts/run-benchmark.mjs --target /path/to/project --html /path/to/report.html
```

The skill's Node scripts require Node.js 20+. Generated projects require Bash and `jq` for `scripts/check-state.sh`; `init.sh` additionally requires tools used by the detected project stack.

## What It Creates

| File | Purpose |
|---|---|
| `AGENTS.md` | Concise map of startup, invariants, verification, and project knowledge |
| `feature_index.json` | Minimal feature index: id, title, status, priority, depends_on |
| `features/feat-001.md` | Feature detail placeholder: objective, done criteria, plan, evidence |
| `init.sh` | Health check script with `quick` (default) and `full` modes |
| `progress.md` | Append-only session log |
| `docs/README.md` | Map of the project's minimal evidence-grounded documentation set |
| `scripts/check-state.sh` | Validate semantic state with `jq`, then show active/blocked/todo features and progress |

Fresh output is idle: `feat-001` and `feat-002` are `todo`. Zero or one active
feature is valid, and the agent does not promote a todo feature without
instruction. Each entry in `feature_index.json` uses `id`, `title`, `status`,
`priority`, and `depends_on`. `scripts/check-state.sh` validates that schema and its
state invariants (including dependencies, at most one active feature, required
active detail, and a valid work state) before printing state. It exits nonzero
on malformed or invalid state.

## init.sh modes

```bash
./init.sh        # quick: available fast/static check — use at startup
./init.sh full   # full: configured lint + static/type + test checks
```

`quick` keeps full-mode checks not applicable. In either mode, a configured
command that fails fails `init.sh`; a command that is absent is reported as a
warning or not applicable and does not fail the script.

## What validate-harness Checks

Five subsystems scored 1–5:

1. **Instructions** — AGENTS.md has startup workflow, done definition, verification commands
2. **State** — feature_index.json valid, progress.md present, feature detail files exist
3. **Verification** — init.sh present and has quick/full modes
4. **Scope** — one-feature rule, done criteria, depends_on tracked
5. **Lifecycle** — end-of-session procedure, append-only progress log

The score is heuristic: it summarizes structural signals and is not a quality
measurement. The validator also enforces hard state/file gates, so invalid
semantic state or missing required files fails validation regardless of score.
It does not replace real before/after agent-session testing.

`templates/detailed-plan.md` is an opt-in linked-plan template for complex or
high-risk work; the generator does not create it by default.

The generator creates `docs/README.md` as the documentation map, then the initializer agent evaluates which project documents are actually needed. `templates/architecture.md` is optional: use it only when repository evidence shows that durable architecture knowledge is repeatedly needed, and list the resulting document in the map. The generator does not infer architecture or conventions.

## Boundaries

Harness engineering only. Not for model selection, prompt tuning alone, or designing application architecture. Keep project facts in the target repository. The generated AGENTS.md is concise rather than artificially short: it contains load-bearing routing and invariants, follows the repository's Markdown style, and does not hard-wrap prose automatically. Specialized documentation exists only when evidence justifies its maintenance. Baseline failures should be recorded and escalated when blocking; unrelated repairs require authorization. harness-slim does not impose a universal commit policy.
